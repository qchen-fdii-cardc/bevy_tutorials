# Rust in Bevy 05：命令意图建模与生命周期安全

「调用 `commands.spawn` 的那一行就等于实体已存在」会直接误判系统因果。`Commands` 的核心价值是把副作用排队到安全应用点，再由调度阶段统一落地。

## 本章 Rust 地图

| Bevy 表面 | Rust 构造 | 设计含义 |
| --- | --- | --- |
| `Commands` | 延迟执行的命令缓冲 | 读取阶段与写入阶段解耦，避免遍历时改集合 |
| `commands.add(MyCommand { ... })` | trait object 风格命令封装 | 用类型承载「意图」，将副作用延后到生命周期边界 |
| `Entity` | 轻量句柄与拷贝语义 | 先记录目标，再在应用阶段验证其是否仍存活 |
| `apply_deferred` / 调度边界 | 阶段化执行模型 | 明确「何时可见」与「何时生效」的时间线 |
| `Result` / 显式分支 | 失败路径建模 | 目标失效、重复销毁等情况可被安全处理 |

## 延迟命令先定义时间线

`Commands` 收集的是「待执行变更」，当前系统拿到的 `Query` 仍是本阶段快照。读写分离带来两个直接收益：遍历稳定、并行分析可行。代价同样清晰：同帧里你提交的生成或销毁请求，通常要到命令应用点后才对后续逻辑可见。

因此生命周期问题先画时间线：意图在何处产生、在哪个调度边界落地、哪个系统负责观察结果。时间线画清楚，很多「偶发 bug」会退化成可复现的阶段错位。

## 所有权边界：System 只提交意图

System 拥有 `&mut Commands` 的短借用权，World 的真实结构修改权由调度器在应用阶段集中执行。这是典型 Rust 边界设计：调用点描述意图，执行点统一兑现副作用，避免多个系统在同一遍历窗口争抢结构性写入。

`Entity` 句柄可以被记录和传递，但它只代表「可能有效的目标」。命令真正执行时，实体可能已被其他命令回收。把这类不确定性写成显式分支，比假设句柄永久有效更接近真实运行条件。

## 用命令类型建模业务意图

把 `spawn`、`despawn` 散落在各系统很快会变成生命周期债务。更稳的做法是定义小而专一的命令类型，例如 `SpawnProjectile`、`ExpireEntity`：字段只携带执行所需数据，`apply` 中只做单一副作用。

这样做的收益是可审计性：你可以按命令类型追踪「谁有权创建实体、谁有权结束生命周期」。当规则升级到分层队列、重放、回滚时，意图模型还能直接复用。

## 生命周期安全来自失败路径

命令系统里最危险的常见假设是「目标一定还在」。把「可能不存在」写进 API 和控制流，生命周期才安全：  
- 销毁前先验证实体是否存在；  
- 多次销毁视为幂等操作；  
- 依赖父子关系的命令在应用点再次确认关系有效。  

这些分支会增加少量样板，却换来跨帧一致性和调试可解释性。

## 小练习

定义一个 `ExpireAfter { entity: Entity, ttl_ticks: u32 }` 意图：倒计时逻辑在普通 System 中维护，真正 `despawn` 放进命令应用阶段。然后回答三个问题：同帧重复提交会怎样、实体提前被移除会怎样、日志该记录意图创建时刻还是命令生效时刻。
